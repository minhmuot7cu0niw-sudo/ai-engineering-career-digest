## 工程实践

### [用 LiteLLM Lens 从大量代理轨迹中识别重复失败](https://docs.litellm.ai/blog/lens-failure-patterns)

- 来源：Hacker News
- 摘要：LiteLLM Lens 介绍如何从数千条 agent traces 中发现重复的失败模式。
- 为什么重要：代理问题往往不是单次错误，而是工具调用、提示或流程在不同任务中反复失败；批量轨迹分析可以把调试从个案排查推进到系统性改进。
- 下一步：为代理记录任务、工具调用、错误和最终结果，按失败类型聚合并优先修复重复率最高的问题。


### [Schema-guard 用于阻止 AI 代理编造 SQL 列名](https://github.com/idk-arsh/schema-guard)

- 来源：Hacker News
- 摘要：Schema-guard 面向 AI 代理生成 SQL 时的列名幻觉问题，提供 schema 约束方向。
- 为什么重要：自然语言到 SQL 的错误可能直接导致查询失败或产生错误结果，数据库 schema 校验应成为代理执行前的边界检查。
- 下一步：在 SQL 执行前加入表名、列名和查询结构校验；校验失败时返回可修正的错误信息，而不是直接执行。


### [Claude Code 增加代理工具调用和 agentId 相关事件信息](https://github.com/anthropics/claude-code/releases/tag/v2.1.290)

- 来源：GitHub Release: anthropics/claude-code
- 摘要：该版本在 turn.step hook 结果中加入 serverToolUses，并在 tool.check 事件中加入 agentId 等信息。
- 为什么重要：更细粒度的工具调用和代理身份信息有助于审计、调试和区分不同代理在复杂工作流中的行为。
- 下一步：检查现有插件或 hook 是否能利用这些事件记录工具调用的名称、输入、起止时间和所属代理。


### [Moching 提供带有 219 个内置工具的 Rust AI 桌面代理](https://github.com/moching-ai-dev/moching)

- 来源：Hacker News
- 摘要：Moching 是一个使用 Rust 构建的 AI 桌面代理，包含 219 个内置工具。
- 为什么重要：桌面代理的能力边界取决于工具数量、权限和调用可靠性；大量工具也会增加选择错误、权限控制和测试的复杂度。
- 下一步：设计桌面代理时建立工具目录、权限分级和逐工具测试集，避免仅通过增加工具数量扩展能力。
